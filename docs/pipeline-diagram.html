Component Reference

scf-check-mapping.json
Primary input for M365 checks (278 of 306 total)
The source of truth for all M365-surface checks. The 28 AZ-* (Azure ARM) checks come from a separate file — az-assess-source-checks.json — which carries its own pre-populated scf {} and frameworks {} objects and bypasses the DB lookup entirely. Most fields here are hand-authored; impactRationale is the exception — it is written back into this file by Generate-ImpactRationale.py. Build-ScfMigration.py can also seed it as a draft when onboarding a new batch of checks.
  • checkId Unique identifier (e.g. ENTRA-ADMIN-001) — also the join key used by M365-Assess collectors.
  • scfPrimary The SCF control ID (e.g. IAC-21.3) used to look up all governance metadata from the DB.
  • scfAdditional Extra SCF controls whose risks and threats are merged in — useful when a check spans multiple governance areas.
  • cisM365ControlId / cisaScubaControlId / stigControlId Manual framework references for frameworks that have no presence in the SCF database.
  • impactSeverity CheckID's own risk rating (Low / Medium / High / Critical), independent of SCF weighting.
  • impactRationale Auto-generated by Generate-ImpactRationale.py — written back into this file in-place.
  • remediation Hand-authored M365-specific fix guidance — UI navigation path or PowerShell command to resolve a failing check.
framework-overrides.json
Gap-fill — patches SCF DB coverage holes per check
The SCF database maps controls to frameworks at the control level, but its coverage is uneven — some checks need framework IDs that the DB simply doesn't carry for their SCF control. This file supplies those missing mappings.
  • Keyed by checkId, so overrides are surgical — one check at a time.
  • mode: replace (default) adds a framework entry only if it's absent from the DB-derived set.
  • mode: append merges additional control IDs into an existing framework entry — used when the DB has partial coverage and the manual entry extends it.
  • Common use: adding CMMC L2 practice IDs for checks where SCF's CMMC mapping is incomplete or missing entirely.
scf.db → controls
Core governance metadata for each SCF control
The primary table in the SCF SQLite database. Queried once at build time using scfPrimary as the lookup key. Contributes most of the content inside the scf {} output object.
  • scf_domain The governance domain (e.g. Identification & Authentication).
  • control_name The full SCF control question — the governance requirement being assessed.
  • csf_function NIST CSF function bucket: Identify / Protect / Detect / Respond / Recover.
  • relative_weighting SCF's numeric risk weight (1–20); combined with impactSeverity to form the impactRating output block.
  • cmm_0–5 Capability Maturity Model flags — indicates which maturity levels this control applies to.
scf.db → assessment_objectives
Per-control auditor questions from the SCF framework
Stores the structured assessment questions that an auditor would ask to verify a control is in place. Each objective has a numbered ID (e.g. IAC-21.3_A01) and a text statement.
  • One control can have multiple objectives — they're collected into an array in the output.
  • These map directly to the assessmentObjectives array in the scf {} output block.
  • Useful for audit tooling that needs to generate evidence-collection checklists from check data.
scf.db → control_risks & control_threats
Risk and threat taxonomy linked to each control
Join tables that associate SCF risk IDs and threat IDs with controls. Both are queried for the primary control and any additional controls, then merged into a single deduplicated list.
  • risks Reference SCF's risk taxonomy — e.g. R-AC-1 (Access Control risk). Help consumers understand the risk categories a failing check contributes to.
  • threats Reference SCF's MITRE-aligned threat taxonomy — e.g. MT-1. Useful for threat-modeling workflows.
  • The union across primary + additional controls means a multi-domain check accumulates all relevant risk/threat IDs.
scf.db → control_mappings
The bridge from SCF controls to external compliance frameworks
The most data-rich table in the pipeline. For each SCF control, it holds the corresponding control IDs in every framework that SecFrame has mapped. This is where the multi-framework coverage in registry.json actually comes from.
  • Uses a numeric framework_id — translated to a human-readable CheckID key by scf-framework-map.json.
  • Covers 10+ frameworks: NIST 800-53, NIST CSF, CMMC, PCI DSS, ISO 27001, HIPAA, SOX, GDPR, and more.
  • If a sub-control (e.g. IAC-21.3) has no mapping for a framework, the build script falls back to the parent control (IAC-21) automatically.
  • CIS M365, CISA ScuBA, and STIG are not in this table — those come from the input file directly.
scf-framework-map.json
ID translation table — DB integer → CheckID key
The SCF database identifies frameworks by opaque integer IDs (e.g. 45, 72). This file is the lookup table that translates those integers to the stable string keys used in CheckID's output (e.g. nist-800-53, pci-dss).
  • Also specifies which DB IDs map to the same CheckID key — some frameworks have multiple DB entries (e.g. NIST 800-53 Rev 4 and Rev 5 are separate DB rows but merge into one output key).
  • Controls which frameworks are included in the registry — any DB framework_id not listed here is silently ignored.
  • Generated by Build-FrameworkTitles.py and committed; not edited by hand.
framework-titles.json
Human-readable titles for framework control IDs
Maps individual framework control IDs to their descriptive titles — e.g. AC-6 → "Least Privilege", PR.AA-05 → "Access permissions and entitlements are managed".
  • Titles are written into the title field on each framework entry in the output, making the registry human-readable without requiring a separate lookup.
  • Generated by Build-FrameworkTitles.py from the SCF DB — not edited by hand.
  • Only applies to DB-derived frameworks. CIS M365, CISA ScuBA, and STIG entries get titles from their own source files.
Build-Registry.py
The build script — orchestrates all inputs into registry.json
The single script that reads every input, runs all SQL queries, and assembles the final output. Run manually or in CI; the output is committed as a static file. Consumers never query the DB themselves.
  • Loads all DB tables into memory at startup (one pass), then processes each check entry without additional queries.
  • Falls back from sub-control to parent control when a framework mapping is missing.
  • Handles the AZ-* surface check path separately — those checks come from az-assess-source-checks.json and bypass the main SCF lookup, copying only the fields their source already provides.
  • Applies overrides last, after DB-derived and manual frameworks are assembled — ensuring the override only fills genuine gaps.
registry.json
The output — fully denormalized, static, consumer-ready
The single file all consumers read. Every check object is fully self-contained — no joins, no DB access needed at query time. Schema v2.0.0, validated against registry.schema.json in CI.
  • scf {} Full governance context: control name, domain, CSF function, maturity levels, assessment objectives, risks, threats.
  • frameworks {} All compliance framework mappings in one place — 18 frameworks, each with control IDs and human-readable titles.
  • impactRating {} Combines CheckID's impactSeverity with SCF's numeric weighting into a single risk signal.
  • remediation M365-specific fix steps — present on ~215 of 278 checks (28 AZ-* and some others have no remediation text yet).
Consumers
Downstream projects that depend on registry.json
All consumers treat registry.json as a read-only data dependency. They sync it as a static file — no submodule, no module installation, no DB access.
  • M365-Assess — uses checkId to key collector output, reads frameworks for compliance reporting, and will read remediation to replace hardcoded fix text in collector scripts.
  • EZ-CMMC — reads CMMC framework entries from frameworks.cmmc to identify non-M365 practices that need procedural or architectural controls.
  • SecFrame — the upstream that owns the SCF DB; CheckID flows data from SecFrame, not to it. SecFrame needs no changes when CheckID's schema evolves.
